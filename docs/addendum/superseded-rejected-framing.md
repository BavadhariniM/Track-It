# Superseded / Rejected Framing

- **v1 → v2 reversal on timezone/DST**: v1 §57 listed "daylight-saving changes" and "time zones" as edge cases the implementation *must* explicitly handle. v2 explicitly reverses this — the single-device, single-user assumption removes the need, and the app deliberately does not implement timezone/DST handling. The PRD (NFR-3) follows v2, not v1, on this point.
- **v1's open "priority options" and "come up with other options"** notes (goal priority field, additional custom-recurrence patterns) were unresolved authoring artifacts in the draft, not real requirements ambiguity — the recurrence side was resolved above; priority was not carried forward (see Data Model Notes).
- **v2's original MVP deferral of advanced/custom recurrence** ("Advanced recurrence can be implemented after the MVP") and **brief.md's explicit exclusion of "advanced recurrence"** from v1 scope were both consciously overridden during this PRD's creation — full exotic scheduling is now in MVP. This is a deliberate scope decision, not an oversight; see `.memlog.md` for the decision record.
- **v1 §19 Future Extensibility** (percentage targets, increasing/decreasing targets, streak-dependent targets, conditional goals, goal dependencies, time-of-day requirements, duration tracking, numeric accumulation, multiple measurements per day) was evaluated during PRD creation and deliberately kept out of MVP, distinct from the recurrence exoticness which was pulled in. The rule engine should remain extensible enough not to preclude these later, but none are built now — see PRD §6 Non-Goals.
- **brief.md's timestamped multi-entry-per-day commitment** ("in for v1," e.g. water logged separately at 8am/12pm/5pm with per-entry notes) was narrowed during PRD creation to a simpler mechanism: a Counter Goal can be incremented repeatedly through the day, but each increment is not individually timestamped or noted — all increments fold into one running daily total (PRD FR-14). This satisfies the same underlying user need (log the same goal more than once a day) without the timestamp/per-entry bookkeeping brief.md described. Confirmed directly with the user during PRD finalization, not an oversight.
- **brief.md's "undecided" stance on wider-audience use** ("Whether this later serves a wider audience beyond personal use is undecided; the design does not currently assume or require it") was firmed up during PRD creation into a permanent architectural commitment: single-user, forever, by design, with no multi-user data model to grow into (PRD §2.2). This was confirmed explicitly and repeated twice by the user during this PRD's creation (see `.memlog.md`), so it is a deliberate narrowing of brief.md's deliberately open question, not an oversight.
