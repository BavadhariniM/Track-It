- (constraint) Offline-first, absolute: no server, no account/login, no cloud dependency (NFR-1, brief). No telemetry/analytics/crash reporting of any kind, ever (NFR-2).
- (constraint) Calendar/day status is always derived, never a stored source of truth; any stored per-day status is a read-optimization cache only, serving widgets (FR-31) and long-range stats (FR-28), provably re-derivable from rules+logs+cheat-days at any time (FR-4, addendum caching-policy).
- (constraint) Goal edits/pauses/resumes must version instead of mutate: historical days evaluate against the Version active on that date (FR-3). Addendum suggests a three-table split (goals / goal_versions / goal_logs) to support this without mutating historical evaluation -- not yet ratified as an AD.
- (constraint) Flutter + Dart, single shared codebase targeting Android and iOS with functional parity as the stated bar for success (brief, NFR-5). Local database engine is explicitly unspecified in source docs -- architecture's call, not product's (addendum technology-platform note).
- (constraint) [ADOPTED] Custom-recurrence anchor date is settled at PRD level: every-N-days/weeks/months cycles anchor to the Goal's start date and are not re-anchored by edits; Nth-weekday-of-month is computed per-calendar-month independent of start date (FR-9). Architecture must encode this, not re-decide it.
- (constraint) Multiple entries per day per Goal must not be precluded by the data model, even though MVP UI only exposes one aggregated daily value (addendum data-model-notes, v1 21).
- (constraint) Import (FR-34) must always prompt on conflict, never silently resolve; exact conflict-prompt UX is deferred to UX phase, not architecture (addendum evaluator-design note).
- (event) Run initialized from docs/brief.md, docs/prd/ (status: final), docs/addendum/, docs/planning/ memlogs and review-rubric. Coaching path selected. Deliverable scope: spine + data-model ERD + evaluator decision-flow diagram.
- (decision) Design paradigm: layered/hexagonal split into domain (Goal/GoalVersion/GoalLog entities + the evaluator, zero Flutter/DB imports), data (Drift-backed repositories implementing domain-defined interfaces), presentation (screens/widgets, Riverpod). Binds: all. Prevents: the evaluator being reimplemented or diverging between the live-calendar path and the cached widget/stats path, and domain logic becoming untestable by entangling it with UI or storage. Rule: domain layer has zero imports of Flutter or Drift; data and presentation depend on domain, never the reverse.
- (decision) State management + DI: Riverpod 3.x (code-gen style, @riverpod). Binds: presentation layer, cross-layer DI (repository/evaluator injection). Prevents: BuildContext-coupled domain access, untestable providers. Rule: all cross-layer dependencies (repositories, the evaluator, services) are exposed as Riverpod providers; no direct singleton/service-locator access.
- (version) Riverpod chosen as current (2026) default recommendation for new Flutter projects on the 3.x stable line; flutter_riverpod / riverpod_generator actively maintained per pub.dev, verified via web search 2026-08-17.
- (decision) Persistence: Drift (typesafe reactive SQL over bundled sqlite3) as the sole local datastore. Binds: data layer, goals/goal_versions/goal_logs schema. Prevents: hand-rolled reactive/pub-sub plumbing for calendar recompute, and NoSQL-shaped workarounds for relational queries (period boundaries, rolling-window aggregation, multi-entry-per-day sums) that the addendum's data model requires. Rule: all local persistence goes through Drift; no parallel storage mechanism (e.g. shared_preferences) for domain data, only for simple user settings (week-start day, reminder time).
- (version) Drift confirmed actively maintained in 2026, bundles its own sqlite3 (no native setup) since v2.32.0, reactive streams native fit for live calendar recompute; verified via web search 2026-08-17 (drift.simonbinder.eu, pub.dev).
- (event) User confirmed paradigm (layered/hexagonal) + Riverpod 3.x + Drift as locked-in ADs.
- (decision) Evaluator design for mid-period Version boundaries (Option C, user delegated pick): a Version boundary always splits the period; no pro-rating. When a Goal Version changes mid-period, the current period is truncated at the boundary and a fresh period starts at the new Version's start date, each segment evaluated against its own Version's un-prorated target for however many days it covers. Binds: evaluator, FR-3, FR-4, FR-7. Prevents: an evaluator that pro-rates targets (undefined formula, not specified anywhere) or one that retroactively reassigns a whole period's target to a later Version (violates FR-3's per-date Version guarantee). Rule: period boundaries = calendar boundary (FR-7) INTERSECTED with Version boundaries; a Version's evaluation window is [version.startDate, next-version.startDate or goal end]; each window's periods are evaluated solely against that Version's rules, no cross-Version blending.
- (event) Resolved: PRD-9 / addendum evaluator-design open question. This closes the two questions PRD-9 flagged as deferred to architecture (evaluator design + import-conflict UX -- the latter remains deferred to UX phase per addendum, not architecture's to decide).
- (decision) State-mutation ownership: a single domain-layer GoalService is the only component permitted to create a GoalVersion (edits to target/eligible-days/pause/resume all route through it); a GoalVersion is never mutated in place once GoalLogs exist against it. Binds: FR-2, FR-3, FR-15. Prevents: repositories or UI creating/mutating versions directly, leading to divergent versioning behavior between screens/import. Rule: GoalVersion creation is GoalService-only; the correction-delta floor (floored at 0, FR-15) is enforced inside the domain GoalLog aggregate itself, not in UI or import code, so no caller (including import) can bypass it.
- (decision) Cache write path: the per-day status cache (read-optimization only, see caching-policy constraint) is written solely by a domain-layer use-case invoking a data-layer StatusCacheWriter, triggered only by: a GoalLog write committing, a GoalVersion write committing, or the midnight-rollover job (FR-20). Binds: FR-4, FR-20, FR-28, FR-31. Prevents: UI or ad-hoc code paths writing cache directly, cache drift from source data, partial/incremental-only rebuild logic that can't recover from corruption. Rule: StatusCacheWriter is the only writer; the cache must support full wholesale recompute from rules+logs alone at any time (corrupted/deleted cache = rebuild, not data loss).
- (decision) Evaluator contract: one pure function 'DayStatus evaluate({Goal goal, List~GoalVersion~ versions, List~GoalLog~ logs, DateTime date})' -- no I/O, no Flutter imports, no Drift imports, deterministic. Binds: domain layer, NFR-6. Prevents: evaluation logic leaking into repositories, widgets, or the cache writer, which would make the hardest edge cases (versioning boundaries, rolling windows, cheat-day/exact-target interaction) untestable in isolation. Rule: all four callers (live calendar, cache writer, stats, widget precompute) call this same function; none re-implements evaluation logic.
- (convention) Ids: UUIDv4 strings. Calendar days: naive ISO-8601 date-only strings (YYYY-MM-DD), never DateTime-with-timezone -- matches NFR-3 (no timezone/DST handling); there is nothing to convert if a day is just a date string. Domain failures: Result/Either-style return type from domain/use-case calls, not thrown exceptions -- so the evaluator and services can't silently throw past a caller.

- (decision) AD-4 amended: evaluate() signature extended to {Goal, versions, logs, cheatDays: List<CheatDay>, blackoutDates: List<BlackoutDate>, date} -- FR-4 explicitly names Cheat Days as a status-computation input, and FR-10 requires Blackout Dates to exempt a date without changing eligible-day count. Also adds a determinism rule: evaluate() sorts versions by versionStartDate and logs by date internally; callers may pass any order.
- (decision) Data model amended: add CHEAT_DAY (id, goalId, date, note) and BLACKOUT_DATE (id, goalId, date, reason) entities to the ERD -- the quota (GOAL_VERSION.cheatDayQuota) was modeled but the per-date designations it quotas were not. DNF marking (FR-17) added as a GOAL_LOG.dnfMarked bool field only, not a separate table or evaluate() input, since FR-17 states the mark is display-only and is superseded by the period's actual computed outcome once closed.
- (decision) AD-6 tightened: GoalService is now stated as the sole writer of BOTH GoalVersion and GoalLog (previously only clearly stated for Version); the correction-delta floor is enforced by GoalService before persisting a GoalLog, not merely 'inside the aggregate' (which read as bypassable by a repository calling the aggregate directly). Added tie-break: GoalService enforces at most one GoalVersion per (goalId, versionStartDate); a same-day second edit amends the still-log-free Version in place, but is rejected once any GoalLog exists against it (user must pick a later effective date).
- (decision) AD-1/AD-7 layering conflict resolved: domain defines an abstract CacheWriter interface (same repository-interface pattern as AD-3's persistence repositories); the data layer supplies the Drift-backed implementation. The domain use-case that triggers cache writes depends only on this interface, so AD-1's 'domain depends on nothing' still holds -- domain never imports Drift.
- (decision) New AD-8: streak/rollup ownership. A domain StatsService computes Streaks (FR-29) and rollups (FR-28) by reading cached DayStatus rows (falling back to evaluate() for any uncached range) -- no separate streak cache, keeping AD-7's cache row shape to bare DayStatus only. Binds: FR-28, FR-29, NFR-6. Prevents: streak logic being duplicated/diverging between the dashboard, goal detail screen, and widgets.
- (decision) Import/export (FR-33/34) and Reset/Erase-All (FR-36) ownership made explicit: JSON (de)serialization lives in data/io/; all writes produced by import route through GoalService like any other mutation (already covered by the tightened AD-6). Reset/Erase-All is a domain use-case that clears all Drift tables plus the settings store inside one transaction.
- (decision) Atomicity convention added (FR-19, NFR-7): every multi-statement domain mutation (a GoalLog write plus its triggered cache invalidation, a GoalVersion creation, Reset/Erase-All) executes inside a single Drift transaction -- a kill mid-save loses at most the one in-flight, uncommitted entry.
