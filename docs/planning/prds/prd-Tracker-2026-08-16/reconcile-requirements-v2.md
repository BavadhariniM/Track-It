# Reconciliation: requirements-v2.md vs. PRD

**Input checked:** `Requirements/requirements-v2.md` (v2, authoritative/most-resolved requirements doc)
**Checked against:** `prd.md` and `addendum.md`

Note: the intentional MVP-scope override on exotic custom recurrence (v2 said "Advanced recurrence can be implemented after the MVP"; PRD ships it in MVP) is a known, documented deviation (see addendum.md "Superseded / Rejected Framing") and is **not** treated as a gap below.

## Gaps found (5)

- **Midnight rollover behavior is entirely absent (v2 §6.3).** v2 specifies a precise, two-step rule for when the app is left open across midnight: (1) any unsaved, mid-edit entry (a counter being typed, a Boolean toggle not yet committed) is auto-committed to the *old* day, not the new one, and (2) the app then performs a full data reload so goal statuses/Today page/in-memory evaluation state recompute against the new local day. This is also listed as a required edge case in v2 §37. Neither `prd.md`'s FRs nor `addendum.md` mention this behavior at all — there is no FR covering what happens to an in-progress entry when the calendar day changes while the app is open.

- **Cheat-day exemption is narrowed to "Exactly" only, dropping v2's explicit uniform-application rule (v2 §25.2).** v2 is careful to state that the cheat-day exemption principle (a cheat day removes that day from consideration rather than adjusting target numbers) "applies uniformly across Minimum, Maximum, Exact, and Range comparison rules." PRD FR-15 states only that a Cheat Day "does not reduce an Exactly target's required count," which flattens the distinction v2 deliberately called out — a reader of FR-15 alone would not know the same non-reduction guarantee applies to At Least, At Most, and Range goals too.

- **Goal Detail Screen drops the "version timeline" as a distinct element (v2 §16.3, §27).** v2 explicitly lists "Version timeline" (e.g. "3x/week Jan 1–Mar 14, 5x/week Mar 15–present," with each segment's date range and rule summary) as a screen element separate from "Historical calendar" — both appear as distinct bullets in v2 §27's list. PRD FR-25 (Goal Detail Screen) lists "historical calendar" but never mentions the version-segment timeline, so the requirement that a user can see the goal's dated rule-change history on its detail screen is not present in the PRD's FR text (even though FR-3/Goal Versioning exists as a data-layer mechanism).

- **Import validation drops the "empty export is a warning, not a rejection" resolution and the cheat-day-config rejection category (v2 §33.2).** v2 explicitly resolves an edge case: an export with zero goals is *not* a hard rejection, it's a distinct warning the user can proceed past — this is called out by name in v2's Important Edge Cases (§37) as a resolved ambiguity. PRD FR-32's rejection list has no mention of empty exports at all (neither as accepted-with-warning nor otherwise). FR-32's rejection list also omits v2's "invalid cheat-day configuration" category (quota referencing a nonexistent goal, or a negative quota) and the "missing required structure (no `goals` array, no `metadata`, etc.)" category, both explicitly named in v2's full rejection list.

- **The daily-vs-weekly evaluation semantic distinction is lost (v2 §12).** v2 goes out of its way to state that "7x/week with 2 cheat days" (a daily-evaluated goal, with a per-day pass/fail/cheat outcome and a real daily streak) and "5x/week" (a weekly-evaluated goal, where only the week as a whole passes/fails and no meaningful daily streak exists) "are not interchangeable representations of the same intent," and that goal-creation UX must make this distinction clear. The PRD's FR-6 (Evaluation Period Types) and FR-27 (Rule-Aware Streaks) capture the mechanics of period-based vs. daily streaks in general, but nowhere restates this specific worked contrast or the requirement that goal-creation guide the user to pick the right one — the distinction v2 was careful to draw is not preserved.
