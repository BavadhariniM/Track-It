# Story 1.11: Midnight Rollover and Data-Loss Bound

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As Panda,
I want an entry I'm mid-typing at midnight to land on the right day, and to never lose more than that one entry if the app is killed,
so that I can trust the app even at the edges of a day.

## Acceptance Criteria

1. **Given** Panda has an uncommitted Counter entry being typed as midnight passes with the app open **When** the clock rolls over **Then** that entry auto-commits to the day it was entered on, not the new day (FR-20)
2. **Given** the rollover just happened **When** it completes **Then** the app performs a full data reload so Dashboard/Day View/in-progress statuses recompute against the new local day, with no interstitial or toast interrupting Panda (FR-20, UX-DR21)
3. **Given** the app is killed mid-save at any other time **When** Panda reopens it **Then** only that single in-flight entry is lost and everything previously committed survives (FR-19, NFR-7)
4. **And** any multi-statement domain mutation (a log write plus its cache invalidation, a version creation) executes inside one Drift transaction, so a kill mid-write can never leave partial state

## Dev Notes

- **This story closes Epic 1 by hardening the transactional/data-durability guarantees every prior story's write paths depend on** — it does not introduce new domain entities or evaluation logic. Its two concerns are: (1) the midnight-specific auto-commit-and-reload behavior (FR-20, new mechanism), and (2) auditing that the transaction-atomicity discipline established in Story 1.1 was actually followed consistently by every subsequent story's write path (FR-19/NFR-7, an audit/hardening pass, not new mechanism).
- **AD-1 (layering) applies to the midnight watcher specifically:** detecting wall-clock midnight is fundamentally a platform/OS-clock concern, which is I/O by nature — this logic must live in `presentation`/composition-root code (e.g. a Riverpod provider observing `DateTime.now()` or a platform timer/lifecycle callback), never inside `domain`. `domain`'s `GoalService.logCounter`/`logBoolean` remain pure business-logic use-cases that receive an explicit `date` parameter — they have no idea "midnight" exists as a concept, and that's correct: the midnight-awareness is entirely a caller-side (presentation-side) responsibility of *which date* to pass into the existing, unchanged `GoalService` API.
- **AD-6 (GoalService as sole writer) applies unchanged:** the midnight auto-commit is not a new bypass write path — it calls the exact same `GoalService.logCounter`/`logBoolean` methods any other user-triggered log write calls, just triggered by a clock event instead of a user tap, and with the date pinned explicitly to the pre-rollover day.
- **Transaction atomicity — the architecture's own convention table is the authority here:** "every multi-statement domain mutation — a `GoalLog` write plus its triggered cache invalidation, a `GoalVersion` creation, Reset/Erase-All — executes inside a single Drift transaction. A kill mid-save loses at most the one in-flight, uncommitted entry; all previously committed data survives." This story's job is to verify every `GoalService` use-case built in Stories 1.1–1.9 actually honors this, and to build the midnight auto-commit to honor it from day one, not retrofit it later.
- **FR-20, verbatim, and the reason auto-commit must target the pre-rollover date:** "If the app is left open across a midnight boundary, any unsaved, mid-edit entry (a Counter being typed, a Boolean toggle not yet committed) is auto-committed to the day it was entered on, not the new day. The app then performs a full data reload so all in-memory evaluation state (dashboard, today's view, in-progress statuses) recomputes against the new local day." Both halves of this are required: correct-date auto-commit, and a full recompute/reload afterward — implementing only one half does not satisfy the AC.
- **UX-DR21 (silent refresh, no interstitial):** the midnight rollover must be invisible as an event to Panda beyond the natural effect of views updating — no toast, no modal, no navigation. This is explicitly called out in EXPERIENCE.md's State Patterns: "surfaced to the user only as the affected views quietly refreshing, not an interstitial or toast."
- **NFR-3 (no timezone/DST) still applies:** "midnight" here means the local device's midnight in whatever timezone the device is currently set to, with no cross-timezone or DST-transition logic — this app has no concept of timezone travel (NFR-3), so the midnight watcher only needs to observe the device's local calendar date advancing, nothing more sophisticated.
- **Anti-duplication guidance:** the midnight auto-commit reuses `GoalService.logCounter`/`logBoolean` unchanged — do not build a separate "rollover write path." The transaction-atomicity audit (Task 3) should not require rewriting any prior story's `GoalService` use-case unless the audit actually finds a violation — if Stories 1.1–1.9 were implemented per their own Dev Notes' transaction guidance, this audit should mostly be confirmation, not remediation.
- **Testing standards:** this story's ACs are precisely NFR-7's territory ("only an in-flight unsaved entry is ever at risk; everything committed survives app kills, crashes, midnight rollovers") — kill-simulation testing across every write path is the primary testing standard here, not just the midnight-specific behavior. Also explicitly test that transaction scoping is not *overly* broad (Task 5.4) — a subtle but real risk when "wrap everything in a transaction" is applied too literally.

### Completion Notes List

- **Scope of "in-flight state" (Subtask 1.3):** audited every write-triggering interaction built in Stories 1.1/1.2/1.9. Only one surface holds a genuinely uncommitted, date-pinned edit that could be silently lost or mis-dated across a midnight boundary: the Counter direct-entry dialog opened via `CounterStepper`'s "Enter an amount" affordance (`lib/presentation/components/counter_stepper.dart`). The +/- stepper buttons and the Boolean toggle (`lib/presentation/screens/day_view.dart`) both call `GoalService.logCounter`/`logBoolean` synchronously and immediately on tap — there is no persistent "typed but not yet saved" state to lose. The goal-creation wizard's in-progress state (Story 1.9, `goal_wizard_provider.dart`) is deliberately treated as **out of scope**: it isn't tied to a specific calendar date the way a Counter/Boolean log entry is (a Goal doesn't have a "day" until it's actually created), and it never calls `GoalService` until its own explicit Save step, so there is no half-written domain state a midnight boundary could corrupt or mis-date — the wizard's own Save path is already covered by Task 3/4's transaction-atomicity audit instead.
- **Making the direct-entry dialog's date explicit (Subtask 1.3 audit):** confirmed `_CounterStepperDialog` (`day_view.dart`) already captures its target `date` once, explicitly, as an immutable widget constructor parameter — it never re-resolves "today" lazily at Save time. This was already correct before this story; what was missing was purely the *proactive* auto-commit-at-rollover mechanism (Task 1), since without it a mid-typed value sitting in the dialog was vulnerable to being lost entirely if the app were killed before the user tapped Save (the actual FR-19/FR-20 data-loss-bound gap this story closes).
- **Rollover-detection mechanism and testability:** `lib/presentation/providers/current_date_provider.dart` exposes `currentDateProvider`, a `@riverpod Stream<DateTime>` that is the single source of "today" for every rollover-aware consumer. Its default implementation ticks a real `Timer.periodic(1s)` comparing date-only `DateTime` values and only emits when the calendar date actually changes; `ref.onDispose` cancels the timer. Tests override it entirely via `currentDateProvider.overrideWith((ref) => controller.stream)` with a plain `StreamController<DateTime>`, letting a rollover be simulated deterministically by pushing synthetic dates — the same `ProviderScope`-override pattern every other I/O-backed provider in this codebase already uses. `lib/presentation/providers/in_flight_edit_provider.dart` (`InFlightEdit`, `keepAlive: true`) holds the single Counter direct-entry edit that may be mid-flight (the dialog is modal, so at most one at a time), capturing `goalId`/`date`/`text` explicitly. `lib/presentation/providers/midnight_rollover_provider.dart` (`MidnightRolloverWatcher`, `keepAlive: true`) uses `ref.listen(currentDateProvider, ..., fireImmediately: true)` inside its own `build()`; the first observed date establishes a baseline (not itself a rollover), and any subsequent different date is treated as a rollover, at which point it reads `inFlightEditProvider`, parses its `text` via `double.tryParse`, and — if parseable — calls the exact same `GoalService.logCounter(goalId:, date:, delta:)` any user-triggered write calls (AD-6, no bypass path), with `date` pinned to the in-flight edit's already-captured pre-rollover value. It then clears the in-flight registry regardless of whether a value was committed (nothing left "in-flight" for a day that's no longer "now"). `CounterStepper`'s direct-entry dialog (now split into `_DirectEntryDialog`, a `ConsumerWidget`) itself watches `inFlightEditProvider` via `ref.listen`; if it's cleared by something other than the dialog's own Save/Cancel handlers, the dialog closes itself silently (`Navigator.pop()`, no return value) — this is what prevents a double-write if the user were to tap Save on a dialog whose value the watcher already auto-committed. The watcher is instantiated once at the composition root (`main.dart`'s `TrackerApp`, now a `ConsumerWidget`) via `ref.watch(midnightRolloverWatcherProvider)`, so it observes for the app's whole lifetime (AD-1: this entire mechanism lives in `presentation`; `GoalService`'s signature and `domain`'s `evaluate()` are untouched by this story).
- **`MonthViewScreen` staleness fix (Task 2):** `_MonthViewScreenState` previously captured `_today`/`_todayMonth` once as `late final` fields in `initState`, so "jump to today" and the isToday ring both went stale after a real midnight rollover. Fixed by converting the screen to `ConsumerStatefulWidget` and making `_today` a mutable field refreshed via `ref.listen<AsyncValue<DateTime>>(currentDateProvider, ...)` inside `build()`, calling `setState` only when the emitted date actually differs (Riverpod's documented pattern for reacting to a provider from a `State`-owning widget without mutating anything mid-build). The page-anchor field was renamed `_pageEpochMonth` and — deliberately — is **not** re-derived from the live date on every rollover: doing so would shift every already-swiped-to page's rendered month out from under a user who had navigated away from "today," which is worse than the staleness bug being fixed. Instead, `_jumpToToday()` computes its target page (`_todayPage`) fresh each time from the *current* `_today` relative to the fixed `_pageEpochMonth` epoch, so a rollover that also crosses a month boundary (e.g. Aug 31 → Sep 1) correctly retargets one page forward without perturbing any other page's mapping. `DayViewScreen` and `WeekViewScreen` were confirmed **not** to have the same bug and were left untouched (per this story's scope boundary): both take their date (`date`/`referenceDate`) as an explicit constructor parameter supplied by their caller on each navigation, rather than capturing "today" internally — `DayViewScreen` pinned to a specific calendar date correctly continues to show that date's data even if it's no longer "today" by the time it's viewed (nothing about that date's evaluation changes), and a fresh instance with the live date is what Month/Week View push on the next navigation.
- **Transaction-atomicity audit (Task 3) — confirmatory, not remedial:** every `GoalService` use-case (`createGoal`, `logBoolean`, `logCounter`, `markBlackoutDate`) was already found wrapped in exactly one `_transactionRunner.run(...)` call per logical operation, including `createGoal`'s Goal+GoalVersion pair in a single transaction (Subtask 3.4). No code changes were needed in `goal_service.dart`. The midnight-rollover auto-commit (Subtask 3.2) is itself trivially covered by this same guarantee since it calls `GoalService.logCounter` unchanged — there is no separate "rollover write path" to audit.
- **Kill-simulation coverage extended (Subtask 5.3/4.2):** `test/domain/services/fakes.dart` gained `InMemoryGoalLogRepository.shouldFailOnUpsert` and `InMemoryBlackoutDateRepository.shouldFailOnInsert` (alongside the pre-existing `InMemoryGoalVersionRepository.shouldFailOnInsert`), each simulating a process kill partway through a transaction by throwing before the fake's mutation. `test/domain/services/goal_service_test.dart` gained kill-simulation tests for `logCounter` (a failed upsert leaves the prior committed total intact, not a partial write) and `markBlackoutDate` (a failed insert leaves zero rows), extending the existing `createGoal` kill test (Story 1.1's original pattern). Coverage "via the wizard's save path" is satisfied indirectly: the wizard's Review-step Save ultimately calls `GoalService.createGoal` with no additional write logic of its own, so `createGoal`'s existing/extended kill-simulation tests already cover that path's atomicity; per this story's explicit scope boundary, `test/presentation/goal_creation_wizard_test.dart` (Story 1.9) was not touched.
- **Transaction scoping is per-operation, not batched (Subtask 5.4):** added a test asserting two sequential, unrelated `createGoal` calls are independent transactions — a simulated kill during the *second* call's `GoalVersion` insert does not roll back the *first* goal, which remains fully committed. This is true by construction (each `GoalService` method makes its own single `_transactionRunner.run()` call), and the test exists to lock that in against future regression rather than to fix anything.
