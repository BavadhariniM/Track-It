- source_spec: `docs/stories/spec-bug1-day-view-title.md`
  summary: DayViewScreen's AppBar title reads the current date via a one-shot `todayDateOnly()` call rather than watching the reactive `currentDateProvider`, so it will not update live if a user leaves the screen open across a real midnight rollover.
  evidence: `month_view.dart` already demonstrates the reactive pattern (subscribes to `currentDateProvider` to refresh its "today" ring live); wiring the same pattern into `DayViewScreen` would also require adding a `currentDateProvider` override to `test/presentation/day_view_test.dart`'s `buildApp` helper, which is beyond the scope of Bug 1 (title always said "Today" regardless of date — a static-per-navigation bug, not a live-update bug).

- source_spec: `docs/stories/spec-bug1-day-view-title.md`

  evidence: Bug 1's fix added a shared `formatDisplayDate` helper in `domain/evaluator/date_format.dart` and pointed `day_view.dart` at it instead of adding a fourth literal duplicate, but migrating the three pre-existing call sites onto the shared helper was out of scope for a one-shot bug fix (touches three unrelated files/features).

- source_spec: `docs/stories/spec-bug2-reminder-notification-permission.md`

- source_spec: `docs/stories/spec-bug8-today-tab-completion-edit.md`
  summary: On the Today tab, `_DashboardGoalRow`'s write-gate (`periodResolvedElsewhere`) mixes `goalStatus.dayStatus.status` (passed down from the parent's `todayProgressProvider`/rollup-provider snapshot) with `ownLogCompleted` (derived from a freshly, independently watched `goalLogsProvider`) — unlike Day View's `_GoalRowForDate`, which derives both from one local `evaluate()` call over the same already-watched data, so the two values can never disagree. Today's version can theoretically render for one frame with a stale `goalStatus` against fresher `logs`, letting a tap fabricate a duplicate log for a period the parent provider hasn't yet learned was already resolved via another date.
  evidence: Edge Case Hunter and Blind Hunter's independent reviews of Bug 8's diff both flagged this data-source split. Traced the actual risk: `_DashboardGoalRow` is a `ConsumerWidget` that can rebuild on its own `goalLogsProvider(goal.id)` watch firing, independently of its parent (`DashboardScreen`/`_RollupSection`) re-passing a fresh `goalStatus`, since `goalStatus` is a plain constructor parameter, not itself a provider this widget watches — so a genuine one-frame staleness window exists. In practice this requires a second write racing the same goal's status right as the user taps (unlikely for this app's single local user, no concurrent/multi-device writers yet), so it was deferred rather than fixed via a spec loopback; the spec's own boundary ("no `evaluate()` in `dashboard_screen.dart`; status only from `todayProgressProvider`") is what causes this gap, so any real fix means renegotiating that boundary (e.g. allowing a local, evaluate()-free-but-consistent check, or relaxing the no-`evaluate()` rule specifically for this gate) — worth doing if multi-device sync is ever added, not before.
